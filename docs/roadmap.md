# Harness Intelligence Layer 项目计划

## 1. 总体目标

通过共享项目索引、工程知识和 token 预算打包，减少 OpenClaw、Cline、Codex 在同一仓库内的重复搜索与重复上下文输入，同时保持任务成功率。

核心验收指标：

- Context Recall：关键文件和符号是否被召回；
- Context Precision：返回上下文中的无关内容比例；
- Input Token Reduction：相同任务的输入 token 减少量；
- Task Success Rate：任务最终正确完成率；
- Retry Count：平均修复轮次；
- Cost per Successful Task：完成正确任务的总成本；
- Cross-Harness Reuse：一个 Harness 写入的知识能否被另一个复用。

## 4. Phase 2：索引质量与增量更新

进入条件：V0.1 检索存在可量化的召回不足，且问题不是查询表达或调用策略造成的。

进入条件评估（2026-10-05，数据来自 `benchmarks/`）：

- **已量化（修正前）**：中文自然语言任务平均 Context Recall 为 26.9%，补充英文标识符后为 65.7%，均低于 90% 目标；`hinted` 下未召回符号降到 2 个，但仍有 14 / 26 条任务达不到 90%，且分类差异明显（`benchmarks/verify.py` 逐类报告，`cross-module` 明显低于 `bug-localization`）。
- **表达因素已单独测量（修正前）**：仅改变任务表达即可挽回约 39 个百分点（26.9% → 65.7%），说明表达是主要影响因素之一，但剩余缺口与表达方式无关。
- **剩余缺口可归因于两处检索实现问题**：中文连续串被整体当作单一词项，无法与源文件中的局部词匹配；文档文件不声明符号且行较长，在 `score / token_cost` 排序下必然输给代码片段。
- **结论**：进入 Phase 2 是合理的，但优先级应是先做最小可验证的检索修正（中文词项切分、文档片段排序），验证有效后再投入 Tree-sitter 与增量索引。

### Phase 2 第一步：两处最小检索修正（已完成）

新增 `src/harness_intelligence/terms.py`（代码检索与记忆检索共用同一份词项定义），并改写 `retrieval.py` 的评分与选窗：

1. **中文词项切分**：连续中文串不再整体作为一个词项，而是拆成重叠的 2 字与 3 字 n-gram（`重建索引之后` → `重建`、`建索`、`索引`…）。单字不参与匹配（单字几乎命中所有中文行）；词项数上限 200，使粘贴长文时每行扫描次数仍有界（集合式调用方如记忆检索可显式关闭该上限）。
2. **片段级评分**：得分不再按"整个文件的命中行数"计算后套给该文件的所有窗口，而是按"该片段自身包含的命中行数"计算。窗口受 token 上限约束、同文件互不重叠，并按证据密度挑选要发射的窗口（原先只取文件里最靠前的 3 个窗口，且密集命中会合并成一个数百 token 的整段）。路径与符号命中作为文件级加成保留，但各自饱和计数；查询直接写出的标识符（`discover_files`）权重高于只与标识符中某个词相同的情况（`memory` ∈ `test_index_excludes_memory_store`），两者不再等价。

同批做的两处工程性调整：符号名按 `snake_case` / `camelCase` 词部件匹配（`json` 不再命中 `_write_jsonl`）；行命中改为一条预编译正则扫描（原来每行对每个词项做一次 Python 包含判断），使中文任务在词项数变多后延迟不退化。

同一任务集、同预算复测（2026-10-05，26 题 × 1500 token、索引 schema 2）：

| 变体 | 修正前 Recall | 修正后 Recall | 达标（≥90%） | 中位包体积 | 重复片段 |
|---|---|---|---|---|---|
| `raw`（中文自然语言） | 26.9% | 47.8% | 4 → 7 / 26 | ≈1470 token | 0 |
| `hinted`（中文 + 标识符） | 65.7% | 69.9% | 12 → 15 / 26 | ≈1480 token | 0 |

验证：`benchmarks/verify.py` 全绿（本机已装 ripgrep，`file discovery` 由 SKIP 变 PASS，本轮零 `SKIP`；CI 也已显式安装 ripgrep，避免该断言在流水线里长期只输出 SKIP）、102 项单元测试通过、基线已随本次改动用 `--write-baseline` 重录并一起 review。逐类召回（informational，不作门）：`hinted` 架构 86.1%、故障定位 87.5%、跨模块 62.5%、单文件 50.0%。

**第一步退出标准仍未达到**（`hinted` 69.9%、`raw` 47.8%，门槛 90%）。剩余缺口集中在两类，且都不是"符号提取"问题：

- **中文提问 vs 英文代码**：标注要求召回的是英文实现文件，而纯中文提问只在中文文档与中文工程记忆里有词面命中（例如 `HIL-024` 要求 `indexer.py`，中文提问实际召回的是几篇提到"排除目录"的中文文档）。第二步（见下）用一张可 review 的中英词表桥接此类词面缺口，`raw` 因此提升 21.1pp；词表未覆盖的对仍是缺口，只有它们才需要考虑 §6 的 Embedding。
- **同类候选之间的排序**：文档类任务中，测试文件会凭路径命中（`tests/...`）与描述性符号名参与竞争，把真正回答问题的文档挤出预算。修正显著缓解了这一点，但没有消除：`raw` 变体下 `HIL-017`、`HIL-018` 由 0% 升至 100%，而 `hinted` 变体下这两条仍是 0%——提示里写进的标识符会把预算引向代码文件，所以"补充标识符"对代码类任务有效（`hinted` 整体 69.9% 高于 `raw` 47.8%），对文档类任务无效。文档类问题仍应直接读取文档。

测试过并**放弃**的一条规则：为"查询直接写出的标识符所在窗口"强制保留一个发射名额。它在 26 题上逐题结果完全不变（零可测效果），因此不保留未经验证的分支。

### Phase 2 第二步：跨语言词面桥接（已完成）

第一步解决了"中文串切不开"，但中文提问与英文实现之间仍无词面重叠：`索引陈旧检测` 拆成 索引/陈旧/… 后也命中不了 `indexer.py` 或 `staleness_reason`。这是 §4 归因中的第一类缺口，也是本轮直接对症的改动。

新增 `terms.bridged_terms` 与一张小型 `GLOSSARY`（中文短语 → 英文单词，见 `src/harness_intelligence/terms.py`），**只扩展查询侧**，文档侧仍按字面匹配——一份可 review 的词表就是全部跨语言行为，任何被索引文件的匹配语义都不被悄悄改写。两条约束来自实测：

1. **桥接词不享受路径加成**：路径命中是最强加成（8 分），留给调用者明确写出的标识符。把"索引 → index"也接上路径，会让文档类问题被 `tests/test_index_*.py` 的路径命中直接挤掉（`HIL-017` 实测由 100% 掉到 0%）。
2. **桥接词的内容命中按半权计**：译文是"调用者写了什么"的猜测，不是"调用者写了什么"，`BRIDGE_HIT_WEIGHT = 0.5`。全权时桥接词会主导选窗，把持有必需符号的片段挤出（`HIL-022` 的 `test_stdio_server_round_trip`）。

同一任务集、同预算复测（2026-10-08，26 题 × 1500 token、索引 schema 2）：

| 变体 | 桥接前 Recall | 桥接后 Recall | 达标（≥90%） | 中位包体积 | 重复片段 |
|---|---|---|---|---|---|
| `raw`（中文自然语言） | 47.8% | **68.9%** | 7 → 11 / 26 | ≈1470 token | 0 |
| `hinted`（中文 + 标识符） | 69.9% | 68.9% | 15 → 14 / 26 | ≈1470 token | 0 |

结论：桥接把 `raw` 提高 21.1 个百分点，达标题数 +4，证明"跨语言词面重叠"确是可修复的召回缺口，而不是必须上 embedding 的理由。`hinted` 微降 1.0 个百分点（题目里已有英文标识符，桥接词只是冗余噪声，且 `HIL-022` 的一个必需符号窗被挤出），仍在回归门 8pp / 2 题容差内。**退出标准仍未达到**（`raw` 68.9%、`hinted` 68.9%，门槛 90%）。

仍未解决：`bug-localization` 的 `raw` 仅 41.7%、`hinted` 79.2%，是剩余最弱类别；文档类任务与测试文件的预算竞争、以及更多未进词表的中英对（如 `HIL-001` 仍缺 `indexer.py`、`HIL-025` 仍缺 `file_state`）留给下一轮。词表刻意保持"可判别"：像 `返回/文件/调用` 这类几乎每个文件都出现的词不进表，因为它们买来的是噪声，而噪声同样花掉同一份 token 预算。

计划内容：

状态：上面两处词法层缺陷与跨语言桥接均已修正并量化；下列结构性改动尚未开始。

- 使用 Tree-sitter 替换正则符号提取；
- 构建 import、引用和调用关系；
- 加入 Git 最近变更和历史相关性；
- 增加索引 schema/version 迁移；
- 增加变更文件增量索引和文件监听；
- 返回上下文选择原因及预算淘汰摘要；
- 保留本地词法检索作为强制回退路径。

退出标准：

- Context Recall 不低于 90%；
- 首次索引之外的检索 P95 小于 1 秒；
- 索引更新不会阻塞正常 Harness 工作流。

## 5. Phase 3：跨 Harness A/B 验证

计划内容：

- 对相同任务随机分配 native/control 与 HIL/treatment；
- 记录每轮模型输入 token、工具结果体积、重试次数和最终正确性；
- 验证 Cline 写入的事实可以被 OpenClaw 检索，反向亦然；
- 建立失败回退：HIL 召回不足时允许 Harness 使用原生搜索；
- 分离检索收益与 prompt caching、模型差异造成的收益。

建议成功门槛：

- 中位输入 token 至少降低 20%；
- Context Recall 不低于 90%；
- Task Success Rate 下降不超过 2 个百分点；
- 平均重试次数不增加；
- 跨 Harness 记忆复用成功。

若未达到门槛，应先修正检索与调用策略，不直接增加复杂基础设施。

## 6. Phase 4：按证据扩展

只有出现对应证据时才实施：

- 词法检索无法满足 Recall：增加可选 Embedding 和 Reranker；
- 代码修改质量无法统一比较：增加 Unified Validator；
- 已积累至少 100 个可比任务结果：增加 Model Router；
- 本地索引性能成为瓶颈：评估 FAISS、Qdrant 或其他向量存储。

## 7. 明确不做

- 新 Agent Loop；
- 通用 Shell 或文件编辑工具；
- Session Manager；
- Sub-Agent 框架；
- 自动保存完整聊天流水账；
- V0.1 强制依赖云 Embedding、Qdrant 或 Cross-Encoder；
- 在没有 A/B 数据时宣传固定 token 节省比例。

## 8. 下一步优先级

1. **已完成**：修正两处已量化的检索缺陷——中文词项切分（连续中文串拆为 2/3 字 n-gram）与文档片段排序（片段级评分 + 受 token 上限约束且互不重叠的窗口）。每项都用 `benchmarks/measure.py` 的 `raw` / `hinted` 两次运行验证，并跑 `benchmarks/verify.py` 确认回归门、包不变量与索引覆盖仍成立；基线已用 `--write-baseline` 随改动重录。结果：`raw` 26.9% → 47.8%、`hinted` 65.7% → 69.9%。
2. **已完成**：跨语言词面桥接——`terms.GLOSSARY` 把中文短语映射为英文查询词，只扩展查询侧；桥接词不享受路径加成、内容命中按半权计。结果：`raw` 47.8% → 68.9%（+21.1pp）、`hinted` 69.9% → 68.9%（−1.0pp，回归门容差内）。**仍低于 90% 退出标准**，剩余缺口与逐题回归见 §4。
3. 为 OpenClaw/Cline 各完成至少 10 个 native 与 HIL 对照任务，填写 `benchmarks/results/ab.jsonl`。native 臂的采集与检索改动无关，可立即并行开始；HIL 臂在召回达到可用水平之前不填，否则只是重复测量已知的失败。
4. 汇总未召回文件、重复片段和无关上下文（脚本已输出这些字段）；优先补词表尚未覆盖的中英对，并处理文档/测试文件的预算竞争（`HIL-022` 的符号窗被挤出是两个变体共有的回归）。
5. 召回稳定达到 90% 后，再决定是否投入 Tree-sitter 与增量索引。**现有证据提示 Tree-sitter 解决不了剩余缺口**：未召回的不是"符号没被提取"，而是中文提问与英文实现之间缺少词面重叠（§4）；下一步更可能落在调用策略与跨语言匹配（§6），而不是更精细的符号提取。
5. 达到数据量门槛后再讨论 Validator 和 Model Router。
